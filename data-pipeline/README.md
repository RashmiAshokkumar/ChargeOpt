# Data pipeline

Offline pipeline for ChargeOpt. Run once; it writes `results/results.json`, which the
Django backend reads and seeds its database from (see `backend/api/management/commands/seed_from_pipeline.py`).

## What it does (in order)

1. **Graph construction** — fetches the real drivable OSM road network for a ~4km x
   4km box around Andheri West, Mumbai (`osmnx`/Overpass), simplifies it to an
   undirected graph. Falls back to a synthetic grid graph (clearly labeled as such)
   if OSM is unreachable.
2. **Matrix representations** — dense adjacency matrix, sparse all-pairs shortest-path
   distance matrix (`scipy.sparse.csgraph.dijkstra`), plus an explicit A/A²/A³
   walk-counting demonstration on a small real subgraph.
3. **Centrality** — degree, betweenness, closeness, and eigenvector centrality
   (`networkx`), combined into a composite importance z-score.
4. **Feature vectors + PCA** — 8-feature vector per candidate node; PCA reports
   explained variance and component loadings.
5. **Community detection** — Louvain (`networkx.community.louvain_communities`,
   `resolution=0.05` to get neighborhood-scale zones rather than dozens of tiny
   communities) partitions the graph into sub-regions used for equity constraints.
6. **Candidate shortlist** — top ~60 nodes by composite importance, ≥250m apart,
   excluding nodes within 300m of an existing station.
7. **MCLP optimization** — a real Mixed-Integer Linear Program (PuLP/CBC): binary
   `x_j` (build at candidate j) and `y_i` (demand node i covered), maximizing
   weighted demand covered subject to a budget constraint, road-network coverage
   linkage (not straight-line), and per-sub-region equity constraints. The script
   asserts B=5 vs B=15 produce different, sensible results before writing output —
   if that check fails, it raises rather than shipping a broken model.
8. **Output** — `results/results.json`, including a self-contained
   `optimization_input` block (candidates, demand nodes, coverage sets, sub-region
   membership) so the backend can re-solve the same MILP live for any budget without
   re-running the whole pipeline.

## Data honesty — what's real, proxied, or synthetic

- **Road network**: real OSM data via osmnx/Overpass (`graph_source` field in the
  output records whether a given run actually got live data or fell back to synthetic).
- **Traffic proxy**: derived from OSM road hierarchy + graph centrality. Not live
  traffic data — no such free API exists for this project.
- **Population density proxy**: OSM building-footprint density within 200m of each
  node (a real, OSM-derived signal), falling back to a distance-decay-from-center
  proxy if the building fetch fails. Not WorldPop or Census 2011 data.
- **Existing stations**: `data/existing_stations.csv` is SYNTHETIC — deterministically
  generated by `scripts/generate_synthetic_stations.py` (seeded RNG, plausible
  operator names, scattered across the study bbox). It is explicitly not sourced
  from PlugShare/Google Maps and must never be presented as "manually curated" —
  replace this file with a real curated CSV (same columns: `station_name,
  latitude, longitude, operator, source, notes`) before drawing real-world conclusions.

## Key parameter choices (documented, not arbitrary)

- **Coverage radius = 800m**, not the 2km the brief cites as an *example*. On this
  compact ~4km study area, 2km makes nearly any station blanket-cover the whole box
  (verified: before/after coverage saturated at ~98%→100%, showing almost no
  differentiation). 800m matches real dense-urban EV-charging accessibility
  catchments and produces a genuinely differentiated before/after story.
- **16 synthetic existing stations** — chosen to roughly match plausible current EV
  charging density for an area this size, not tuned to any optimization outcome.
- **Louvain resolution = 0.05** — default resolution produced 49 tiny communities,
  which combined with the equity constraint mandated far more stations than any
  tested budget (making the MILP infeasible). Coarsening to ~12 neighborhood-scale
  sub-regions keeps the equity constraint meaningful without over-constraining the
  budget.

## Typical run

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python scripts/generate_synthetic_stations.py   # (re)generate data/existing_stations.csv
python scripts/run_pipeline.py
```

The script logs each phase and its sanity checks to stdout, and writes
`results/results.json` plus `results/graph_sanity.png`. On first run it fetches
the OSM graph live and caches both the raw graph (`data/andheri_west_raw.graphml`)
and the Overpass HTTP responses (`cache/`) so subsequent runs are fast and don't
re-hit the network.
